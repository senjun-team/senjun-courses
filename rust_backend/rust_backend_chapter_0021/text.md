# Глава 2.1. sqlx и PostgreSQL

В первом модуле данные хранились в памяти процесса и пропадали при каждом перезапуске сервера. Реальному приложению нужно надёжное хранилище, и чаще всего им становится реляционная база данных. В этом модуле мы будем работать с PostgreSQL, а подключаться к ней с помощью крейта sqlx. В этой главе разберём, чем sqlx отличается от других библиотек, запустим PostgreSQL в Docker и подключимся к базе из Rust.

## Способы работы с базой данных

В экосистеме Rust к базе данных можно обращаться на нескольких уровнях абстракций.

1) Самый простой. Драйвер базы данных, например [tokio-postgres](https://docs.rs/tokio-postgres/). Он отправляет SQL-запросы и возвращает строки результата, а всё остальное остаётся на разработчике: преобразование строк в структуры, миграции, пул соединений и т.д.
2) Более высокоуровневый. [ORM](https://blog.skillfactory.ru/glossary/orm/) (Object-Relational Mapping) связывает таблицы с типами Rust и позволяет строить запросы средствами самого языка, без написания SQL в ручную. Самые известные ORM для Rust — [Diesel](https://diesel.rs/), [SeaORM](https://www.sea-ql.org/SeaORM/) и [Toasty](https://github.com/tokio-rs/toasty).

Между ними находится [sqlx](https://docs.rs/sqlx/). Это не ORM, запросы пишутся на сыром SQL, но sqlx берёт на себя всю рутину. Он преобразует результаты в структуры, управляет пулом соединений, применяет миграции и, что важнее всего, умеет проверять корректность SQL-запросов на этапе компиляции.

| Крейт          | Подход                     | Особенности                                                         |
| -------------- | -------------------------- | ------------------------------------------------------------------- |
| tokio-postgres | Асинхронный драйвер        | Полный контроль, но всю обвязку приходится писать самому            |
| sqlx           | SQL с проверкой при сборке | Асинхронный, проверяет запросы по реальной базе на этапе компиляции |
| Diesel         | ORM и построитель запросов | Строгие типы, но синхронный API: для async нужен `diesel-async`     |
| SeaORM         | Асинхронная ORM            | Построена поверх sqlx, удобна для типовых CRUD-операций             |
| Toasty         | Асинхронная ORM            | Разрабатывается командой Tokio, поддерживает SQL и DynamoDB, но пока молодая: версии 0.x |

Мы выбираем sqlx по нескольким причинам. Во-первых, сложные запросы на сыром SQL часто проще, чем через методы ORM. Во-вторых, sqlx асинхронный и работает на Tokio, как и Axum. В-третьих, проверка запросов при компиляции продолжает идею строгости компилятора Rust: опечатка в названии колонки или несовпадение типов становятся ошибкой сборки, а не ошибкой в проде.

У такого подхода есть цена: для проверки запросов во время компиляции нужна запущенная база данных или заранее подготовленный кеш запросов. Подробнее об этом будет в главе 2.3.

## Запуск PostgreSQL в Docker

Устанавливать PostgreSQL в систему не обязательно, будет проще запустить его в [Docker-контейнере](https://habr.com/ru/companies/ruvds/articles/438796/). Так база не засоряет систему, её легко удалить, а нужную версию можно поднять через docker:

```bash
docker run -d --name library-db \
    -e POSTGRES_USER=library \
    -e POSTGRES_PASSWORD=library \
    -e POSTGRES_DB=library \
    -p 5432:5432 \
    postgres:18
```

Переменные окружения `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` задают пользователя, его пароль и базу данных, которая будет создана при первом запуске. Флаг `-p 5432:5432` пробрасывает стандартный порт PostgreSQL из контейнера на компьютер, чтобы к базе можно было подключиться по адресу `localhost:5432`.

Или через [Docker Compose](https://habr.com/ru/companies/ruvds/articles/450312/):

```yaml
services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: library
      POSTGRES_PASSWORD: library
      POSTGRES_DB: library
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U library"]
      interval: 2s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
```

Раздел `volumes` подключает к контейнеру именованный том `pgdata`. Без него данные хранились бы внутри контейнера и пропадали бы при его удалении. Раздел `healthcheck` описывает, как проверить, что база готова принимать соединения. Утилита `pg_isready` входит в образ PostgreSQL.

Запускаем базу и проверяем её состояние:

```bash
docker compose up -d --wait
docker compose ps --format '{{.Name}}: {{.Status}}'
```

Флаг `--wait` заставляет команду дождаться, пока проверка `healthcheck` пройдёт успешно. Подключиться к базе через консольный клиент `psql`, не устанавливая его в систему, можно прямо внутри контейнера:

```bash
docker compose exec db psql -U library
```

Команда `docker compose stop` останавливает контейнер, сохраняя данные, а `docker compose down -v` удаляет контейнер вместе с томом и всеми данными. 

## Подключение sqlx

Добавим sqlx в проект:

```bash
cargo add sqlx --no-default-features \
    --features runtime-tokio,postgres,macros,migrate
```

sqlx поддерживает несколько баз данных и асинхронных рантаймов, поэтому всё нужное включается фичами. `runtime-tokio` позволяет sqlx работать в рантайме Tokio, `postgres` подключает драйвер PostgreSQL, `macros` добавляет макросы для проверки запросов, а `migrate` — поддержку миграций. Флаг `--no-default-features` отключает фичи по умолчанию. Если база данных находится на другом сервере, понадобится шифрование соединения. Для этого добавьте фичу `tls-rustls`. Для локальной базы в Docker она не нужна.

Фичи с пометкой «по умолчанию» включены, если не указать `--no-default-features`. Фичи драйвера и рантайма нужно включать явно: без них sqlx не сможет подключиться к базе.

Адрес базы данных sqlx получает в виде строки подключения. Положим её в файл `.env`:

```env
DATABASE_URL=postgres://library:library@localhost:5432/library
```

Строка подключения состоит из протокола, имени пользователя, пароля, адреса сервера, порта и названия базы данных. Переменная называется именно `DATABASE_URL`, потому что так её ищут макросы sqlx и консольная утилита `sqlx-cli`.

## Пул соединений

Установить соединение с базой данных долго: нужно открыть TCP-соединение, пройти аутентификацию и согласовать параметры сессии. Делать это на каждый запрос к серверу слишком дорого, а одно общее соединение не позволит выполнять запросы параллельно. Поэтому приложения используют пул соединений — набор заранее открытых соединений, которые хендлеры берут на время запроса и возвращают обратно.

В sqlx пул для PostgreSQL называется `PgPool`. Его создают при старте приложения:

```rust
use std::time::Duration;

use anyhow::Context;
use sqlx::postgres::PgPoolOptions;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    dotenvy::dotenv().ok();
    let database_url = std::env::var("DATABASE_URL")
        .context("не задана переменная DATABASE_URL")?;

    let pool = PgPoolOptions::new()
        .max_connections(5)
        .acquire_timeout(Duration::from_secs(3))
        .connect(&database_url)
        .await
        .context("не удалось подключиться к базе данных")?;

    // ...
    Ok(())
}
```

Метод `max_connections` ограничивает число одновременно открытых соединений. У самого PostgreSQL тоже есть лимит соединений, поэтому пул не должен быть больше, чем база готова принять. Для учебного проекта хватит пяти.

Метод `acquire_timeout` задаёт, сколько ждать свободного соединения. По умолчанию это 30 секунд: если база недоступна, каждый запрос к серверу будет висеть полминуты и только потом завершится ошибкой. Короткий таймаут позволяет быстрее ответить клиенту ошибкой.

Метод `connect` сразу открывает первое соединение и проверяет, что база доступна. Если база не запущена, программа остановится при старте, как и положено ошибке конфигурации:

```text
Error: не удалось подключиться к базе данных

Caused by:
    pool timed out while waiting for an open connection
```

`PgPool` внутри устроен как `Arc`, поэтому клонировать его дёшево: все копии работают с одним и тем же набором соединений. Это значит, что пул можно класть в состояние приложения без дополнительной обёртки.

Мы подключились к базе данных, но таблиц в ней пока нет. В следующей главе создадим их с помощью миграций и научимся выполнять запросы.
