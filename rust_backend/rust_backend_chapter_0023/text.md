# Глава 2.3. Макросы и проверка запросов

Функции `query`, `query_as` и `query_scalar` из прошлой главы проверяют SQL только во время выполнения. Если ошибиться в названии колонки или перепутать тип параметра, программа скомпилируется, а ошибка всплывёт только при первом запросе. У sqlx есть макросы с теми же названиями, но с восклицательным знаком на конце: `query!`, `query_as!` и `query_scalar!`. Они проверяют каждый запрос по реальной базе данных ещё на этапе компиляции. В этой главе разберём, как они работают.

## Как работают макросы

Во время компиляции макрос подключается к базе данных по адресу из переменной `DATABASE_URL` и просит PostgreSQL подготовить запрос, не выполняя его. В ответ база сообщает, какие у запроса параметры и колонки результата и какие у них типы. По этим данным макрос проверяет запрос и генерирует код, который подставляет аргументы и разбирает результат.

Макрос `query_as!` заполняет структуру по колонкам результата:

```rust
#[derive(Debug)]
struct Book {
    id: i32,
    isbn: String,
    title: String,
    author: Option<String>,
    pages: i32,
}

async fn get_book(
    pool: &PgPool,
    id: i32,
) -> sqlx::Result<Option<Book>> {
    sqlx::query_as!(
        Book,
        "SELECT id, isbn, title, author, pages
         FROM books WHERE id = $1",
        id
    )
    .fetch_optional(pool)
    .await
}
```

Структуре не нужен трейт `FromRow`: макрос сам знает, какие колонки вернёт запрос, и генерирует код их разбора. Аргументы передаются прямо в макрос после текста запроса, а не методом `bind`.

Макрос `query!` не требует структуры. Он создаёт анонимную структуру, поля которой называются так же, как колонки результата:

```rust
async fn create(
    pool: &PgPool,
    isbn: &str,
    title: &str,
    pages: i32,
) -> sqlx::Result<i32> {
    let record = sqlx::query!(
        "INSERT INTO books (isbn, title, pages)
         VALUES ($1, $2, $3) RETURNING id",
        isbn,
        title,
        pages
    )
    .fetch_one(pool)
    .await?;
    Ok(record.id)
}
```

## Ошибки при компиляции

Посмотрим, какие ошибки ловят макросы. Если ошибиться в названии колонки, сборка остановится с ошибкой от самой базы данных:

```text
error: error returned from database: column "titel" does not exist
  --> src/main.rs:14:5
   |
14 | /     sqlx::query_as!(
15 | |         Book,
```

Если передать аргумент не того типа, например название вместо числа страниц, компилятор укажет на конкретный аргумент:

```text
error[E0308]: mismatched types
  --> src/main.rs:35:9
   |
35 |         title
   |         ^^^^^ expected `i32`, found `&str`
```

Если тип поля структуры не совпадает с колонкой, сборка тоже не пройдёт. Например, колонка `author` может содержать `NULL`, и макрос не позволит объявить поле как `String`:

```text
error[E0277]: the trait bound `String: From<Option<String>>`
is not satisfied
```

Все эти ошибки без макросов проявились бы только во время работы сервера.

## Обязательные и необязательные значения

Чтобы выбрать тип поля, макрос определяет, может ли колонка содержать `NULL`. Для колонок таблицы это просто: у `title` есть ограничение `NOT NULL`, поэтому её тип `String`, а у `author` такого ограничения нет, поэтому её тип `Option<String>`.

Для вычисляемых значений PostgreSQL не всегда может сказать, будет ли там `NULL`, и тогда макрос выбирает `Option`, чтобы не ошибиться. Например, `count(*)` никогда не возвращает `NULL`, но макрос всё равно получит `Option<i64>`:

```rust
let count: Option<i64> =
    sqlx::query_scalar!("SELECT count(*) FROM books")
        .fetch_one(pool)
        .await?;
```

Если вы точно знаете, что `NULL` там не будет, это можно указать в псевдониме колонки. Восклицательный знак после имени делает значение обязательным, и макрос выберет тип `i64` вместо `Option<i64>`:

```rust
let count: i64 = sqlx::query_scalar!(
    r#"SELECT count(*) AS "count!" FROM books"#
)
.fetch_one(pool)
.await?;
```

Вопросительный знак, наоборот, делает значение необязательным: `AS "title?"`. Псевдоним записывается в двойных кавычках, поэтому сам запрос удобно оформить сырой строкой `r#"..."#`.

## Сборка без базы данных

Макросам нужна база данных при каждой компиляции. На компьютере разработчика она запущена в Docker, а в CI её придётся поднимать отдельно ради одной компиляции. При сборке Docker-образа базы данных обычно нет вовсе. Для таких случаев у sqlx есть офлайн-режим: результаты проверки запросов сохраняются в файлы, и макросы берут данные из них, не подключаясь к базе.

Подготовить эти файлы можно командой `cargo sqlx prepare`, пока база запущена:

```bash
cargo sqlx prepare
```

Команда создаёт каталог `.sqlx` с отдельным JSON-файлом для каждого запроса. Каталог добавляют в репозиторий, чтобы сборка без базы работала у всех.

Чтобы макросы использовали `.sqlx`, а не базу данных, задайте переменную `SQLX_OFFLINE`:

```bash
SQLX_OFFLINE=true cargo build
```

Без этой переменной макросы подключаются к базе, если задан `DATABASE_URL`, в том числе через файл `.env`. Поэтому, если база остановлена, сборка завершится ошибкой, даже когда каталог `.sqlx` есть:

```text
error: error communicating with database:
Connection refused (os error 111)
```

Каталог `.sqlx` нужно обновлять после каждого изменения запросов. Если забыть это сделать, сборка в офлайн-режиме упадёт. Проверить, что каталог актуален, можно командой:

```bash
cargo sqlx prepare --check
```

Её удобно запускать в CI: если кеш устарел, команда завершится ошибкой:

```text
error: prepare check failed: .sqlx is missing one or more queries;
you should re-run sqlx prepare
```

## Макросы или функции

Макросы стоит использовать по умолчанию: они превращают ошибки в SQL в ошибки компиляции, а на каждом запросе сразу видно, какие у него параметры и что он возвращает.

Функции `query`, `query_as` и `query_scalar` нужны, когда текст запроса заранее неизвестен и собирается во время выполнения, например при фильтрации по разным наборам полей. Макрос может проверить только запрос, который целиком записан в коде.

Теперь мы умеем писать запросы, которые проверяются при компиляции. Осталось подключить базу данных к серверу на Axum. В следующей главе сделаем API для каталога книг и разберёмся, как разделить код на слои, чтобы HTTP и SQL не смешивались в одном месте.
